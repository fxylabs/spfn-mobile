# 설계 — 앱의 커스텀 라우트를 모바일까지 타입 세이프로 잇는다

작성 2026-08-04. 결정 D-A ~ D-H는 사용자 승인을 받았다.

## 1. 웹에서 지금 무슨 일이 일어나는가

백엔드에 라우트를 추가하면 웹이 자동으로 타입 세이프해지는 메커니즘은 이것이다.

```ts
// 서버
export const appRouter = defineRouter({
    getUser: route.get('/users/:id')
        .input({ params: Type.Object({ id: Type.String() }) })
        .handler(async (c) => { return { id, name } }),
});
export type AppRouter = typeof appRouter;

// 클라이언트
const api = createApi<AppRouter>();
await api.getUser.call({ params: { id: '1' } });
```

두 가지가 이것을 성립시킨다.

| 요소 | 정체 |
| --- | --- |
| 타입 | **코드젠이 0이다.** `typeof appRouter`를 타입 인자로 넘기는 것이 전부다 |
| 전송 | **중계(RPC 프록시).** 클라이언트가 `routeName + input`을 `/api/rpc/<routeName>`에 보내고, 중계가 라우터에서 실제 method·path를 찾는다 |

그리고 라우트가 바뀌면 즉시 드러나는 이유는 따로 있다 — **`spfn:build`와 `spfn:dev` 재시작에 코드젠이 물려 있다.** 라우트를 지우면 다음 빌드에서 심볼이 사라지고 타입 오류가 난다. 계약이 낡을 틈이 없다.

## 2. 모바일에서 무엇이 끊기는가

런타임에 무엇이 실재하는지를 기준으로 갈린다.

| 라우트의 구성 요소 | 런타임에 있나 | 근거 |
| --- | --- | --- |
| method, path | **있다** | `RouteDef.method` / `.path` — 실제 문자열 값 |
| input 스키마 | **있다** | TypeBox `TSchema`. JSON Schema가 런타임 객체다 |
| 응답 타입 | **없다** | `_response: {} as THandlerResponse` — 빈 객체. 컴파일 후 아무것도 남지 않는다 |

**요청 절반은 이미 뽑을 수 있고 응답 절반만 없다.** 웹이 응답 타입을 아는 것은 TypeScript가 handler 반환을 추론하기 때문이고, 그 정보는 다른 언어로 건너가지 못한다.

## 3. 계약이 이미 담을 수 있는 것

| | 상태 |
| --- | --- |
| 스칼라 | `string`, `integer`, `boolean` |
| 배열 | 있다 — `array<T>` |
| 중첩 객체 | 있다 — 다른 타입 이름 참조 |
| 옵셔널 | 있다 — 필드의 `optional` |
| enum·부동소수·map·날짜 | **없다** |

연산 하나의 형태:

```json
{ "id": "echo.send", "method": "POST", "path": "/v1/echo",
  "authProfile": "clientProofV1", "requiresSession": true,
  "requestType": "EchoRequest", "responseType": "EchoResponse" }
```

앱 라우트를 이 형태로 옮기는 것은 자연스럽다. 계약은 이미 REST 연산 목록이고 앱 라우트도 REST다.

## 4. 결정

### D-A. 모바일은 실제 경로로 직접 호출한다

웹의 중계 방식을 모바일이 흉내내지 않는다.

**기존 구현 대조.** 계약은 이미 `restOperations`이고 각 연산이 method·path를 갖는다. 모바일 SDK는 그 형태로 이미 동작한다. 이 항목은 현상 유지다.

**중계를 쓰지 않는 이유.** `clientProofV1`의 서명 대상에 `method`와 `path`가 들어간다. 모든 호출이 `/api/rpc/<routeName>`으로 통일되면 서명이 중계 경로에 걸리고, 어느 연산인지는 본문에만 남는다. `bodySha256`이 본문을 덮으므로 위조는 막히지만, 라우트별 인증 판정이 중계 안으로 들어가 서버 미들웨어 단일 진입점 분기(승인된 결정)와 어긋난다.

### D-B. 응답 모양은 `.output()`으로 선언한다

```ts
route.get('/users/:id')
    .input({ params: Type.Object({ id: Type.String() }) })
    .output(Type.Object({ id: Type.String(), name: Type.String() }))
    .handler(async (c) => ({ id: '1', name: 'a' }))
```

**대안과 기각 사유.**

| 안 | 판정 |
| --- | --- |
| `.output()` 선언 | **채택** |
| TypeScript 타입 추출 (ts-morph 등) | 기각 — 제네릭·조건부 타입을 못 따라가면 **조용히 틀린 타입**을 뽑는다. 틀린 계약은 없는 계약보다 나쁘다 (등록부 P10과 같은 원칙) |
| 응답 타입 없이 느슨한 JSON | 기각 — 요구가 타입 세이프다 |

**부수 이득.** 웹도 응답 검증을 얻는다. 지금 응답은 검증 없이 나간다.

**하위 호환.** `.output()` 없는 기존 라우트는 지금과 똑같이 동작한다.

### D-C. 앱 계약은 앱 저장소가 소유한다

| 계약 | 소유 | 생성 시점 |
| --- | --- | --- |
| 코어(인증·세션·키 수명주기) | spfn-mobile 저장소, 해시로 고정 | SDK 릴리스 |
| 앱(커스텀 라우트) | 앱 저장소 | 앱 빌드 |

**기존 구현 대조.** `tools/contract-codegen/README.md`가 "Input: the bundle named by `Contracts/upstream.lock.json`, and nothing else"라고 못 박고 있다. 이 규칙을 바꾸는 것이 아니라 소유를 나눈다. 앱 계약에서 생성된 코드는 SDK의 `SPFNClient.execute` 위에 얹히므로 SDK를 다시 빌드할 필요가 없다.

### D-D. 타입 문법은 4가지만 추가한다

`enum`, 부동소수(`number`), `map<string, T>`, 날짜 규칙.

**날짜는 새 스칼라를 만들지 않는다.** `integer` 밀리초를 유지하고 필드명 규약(`...AtMillis`)을 계약이 명시한다. 코어 계약이 이미 그렇게 한다.

**열지 않는 것.** 유니온, 제네릭, 재귀 타입. 두 언어의 표현이 갈리고 지금 필요를 대지 못한다.

### D-E. 계약 생성기는 기존 코드젠에 꽂는다

**기존 구현 대조.** `@spfn/core/codegen`은 이미 생성기 플러그인 시스템이고, 내장 생성기 `@spfn/core:route-map`이 라우터를 읽어 `routeName → {method, path}` 맵을 뽑는다. 모바일 계약 생성기는 같은 라우터를 읽어 더 많은 것을 뽑는 것이라 자리가 이미 있다.

### D-F. 배포된 앱을 위한 런타임 장치 3가지

#### 왜 필요한가

빌드 검사가 원리적으로 못 잡는 구간이 하나 있다.

| | 앱 빌드 시점 | 서버 변경 시점 |
| --- | --- | --- |
| 웹 | 같다 | 같다 → 문제 없음 |
| 모바일 | 3개월 전, 이미 스토어에 나감 | 오늘 |

이미 사용자 기기에 있는 앱은 다시 컴파일되지 않는다. 막을 빌드가 없다.

#### 지금 상태

| | 상태 | 근거 |
| --- | --- | --- |
| 계약 버전 비교 로직 | **있다** | `SPFNContractBinding.requireSupported`, 양 플랫폼 SemVer 파서까지 |
| 서버 계약 버전을 받는 경로 | **없다** | `wireMapping.headers`는 인증 헤더 7개뿐 |
| 그 함수의 실사용 | **없다** | 정의 1곳, 테스트 8곳, 프로덕션 0곳 |

검사기는 있고 검사할 값이 도착하지 않는다. 그리고 실제로 어긋난 적이 있다 — 이 문서를 쓸 당시 primitives는 `0.4.0`, spfn-mobile 핀은 `0.3.0`이라 두 범위가 겹치지 않았다. 핀은 그 뒤 `0.4.1`로 올렸지만, 그것을 알아차린 것은 사람이지 SDK가 아니다. 값이 와이어에 실리지 않는 한 다음 어긋남도 같은 방식으로만 발견된다.

#### 세 가지

**1. 계약 버전을 와이어에 싣는다.** 없으면 나머지가 무의미하다.

- 응답 헤더로 서버가, 요청 헤더로 앱이 자기 계약 버전을 알린다.
- `wireMapping`에 들어가고 서명 대상에는 들어가지 않는다 — 진단 정보이지 인증 대상이 아니다.
- SDK는 이미 있는 `requireSupported`를 호출한다. 새로 만들 것은 헤더와 호출부뿐이다.

**2. 연산 단위 가용성.** 연산마다 `since`·`deprecatedIn`·`removedIn`을 둔다. 앱이 실제로 쓰는 연산만 판정 대상이 되므로, 안 쓰는 연산이 사라져도 그 앱은 계속 돈다.

**3. 최소 지원 버전.** 서버가 "이 계약 버전 미만은 거부"를 알리고, SDK가 이름 있는 오류(`appUpdateRequired`)로 올린다. 앱은 업데이트 안내 화면을 띄운다. 없으면 앱은 원인 모를 디코딩 실패만 본다.

#### 계약으로 막을 수 없는 것

타입은 그대로인데 뜻이 바뀌는 경우. `amount`가 원 단위에서 전 단위로 바뀌면 양쪽 다 `integer`라 아무 검사도 안 걸리고, 앱은 100배 틀린 값을 표시한다. 사람이 규율로 막는 수밖에 없다.

### D-G. 계약 표시는 `.contract()`다 — 소비자 이름을 박지 않는다

```ts
getOrder: route.get('/orders/:id')
    .input({ params: ... })
    .output(OrderSchema)
    .contract({ since: '1.0.0', auth: 'clientProofV1' })
    .handler(...)
```

**`.mobile()`을 쓰지 않는 이유.** 소비자 이름을 코드에 박으면 소비자가 늘 때마다 표시가 는다(`.partner()`, `.thirdParty()`). 진짜 성질은 소비자가 누구냐가 아니라 **"버전이 고정된 공개 약속이고 하위호환 없이 못 바꾼다"**이다. 서드파티 API 노출까지 같은 표시로 덮는다.

**`.output()`과 나누는 이유.** 응답 검증은 모든 라우트에 좋고 공개 약속은 일부만 해당한다. 하나가 둘을 겸하면 어드민 라우트에 검증을 걸려다 계약까지 딸려온다.

| 표시 | 뜻 | 없으면 |
| --- | --- | --- |
| `.output()` | 응답 모양을 정한다 | 응답 검증만 없다 |
| `.contract()` | 공개 약속이다 | 내부 라우트. 자유롭게 바꾼다 |

**`.contract()`가 담는 것.** 도입 버전(`since`), 인증 방식(`auth`), 세션 필요 여부, 폐기 표시(`deprecated`).

**폐기된 대안.** 앱이 쓰는 연산을 설정 파일(`.spfnrc.ts`)에 목록으로 선언하는 안은 기각했다. 라우트 정의에서 떨어진 곳에 있어 낡고, 진실(앱 코드가 무엇을 부르는가)의 복사본이라 반드시 어긋난다.

### D-H. 비교 기준은 버전별 파일로 커밋한다

검사가 성립하려면 "이전에 무엇이었나"가 있어야 한다. 클라우드 저장소 없이 저장소 안의 파일로 관리한다.

```
contracts/
  current.json              방금 생성된 것 (빌드마다 갱신)
  released/
    1.0.0.json              고정. 손대지 않는다
    1.1.0.json
  usage/
    ios-1.2.0.json          앱 버전별 사용 목록
    android-1.2.0.json
```

#### 검사 1 — 계약이 깨졌나

백엔드 빌드마다: 라우터를 읽어 `current.json` 생성 → `released/` 중 **가장 최근 것**과 비교 → 파괴적 변경이면 빌드 실패.

| 변경 | 결과 |
| --- | --- |
| 응답 필드 삭제 / 타입 변경 | 실패 |
| 필수 요청 필드 추가 | 실패 |
| 경로·메서드 변경 | 실패 |
| 필드 추가 | 통과 |

**최신 하나만 비교해도 되는 이유.** 하위호환은 전이된다 — 1.1.0이 1.0.0을 만족하고 현재가 1.1.0을 만족하면 현재는 1.0.0도 만족한다. 단 릴리스마다 스냅샷을 빠짐없이 남겨야 이 사슬이 성립한다.

#### 검사 2 — 지워도 되나

연산을 지우려 하면 `usage/` 전체를 훑는다.

```
getOrder cannot be removed:
  ios-1.0.0, ios-1.1.0, android-1.0.0 still call it
```

지금까지 "지워도 되나"를 아무도 몰라서 못 지웠다. 이 목록이 근거를 만든다.

#### 사용 목록은 손으로 안 적는다

앱 빌드가 기록한다. 양쪽 플랫폼에 이미 도구가 있다.

| 플랫폼 | 도구 | 읽는 것 |
| --- | --- | --- |
| Android | R8 (안 쓰는 코드를 지우는 도구) | 무엇이 남고 지워졌는지 리포트 |
| iOS | 링크맵 (링커가 남기는 심볼 목록) | 최종 앱에 들어간 함수 목록 |

생성기가 "연산 10개를 만들었다"를 알고 빌드 결과가 "7개만 남았다"를 알려준다. 차이가 데드 API다. **SDK 코어 연산은 제외한다** — 앱이 직접 안 불러도 SDK 내부가 쓴다.

**데드 API는 경고이지 실패가 아니다.** 이 앱이 안 쓴다고 지워도 되는 것이 아니다. 이전 버전 앱·다른 앱·파트너 연동이 쓸 수 있다.

#### 스냅샷을 만드는 시점

| 무엇 | 누가 | 언제 |
| --- | --- | --- |
| `released/1.1.0.json` | 백엔드 릴리스 명령 | 계약 버전을 올릴 때 |
| `usage/ios-1.2.0.json` | 앱 빌드 | 앱을 릴리스할 때 |

둘 다 명시적 행위다. 매 빌드마다 파일이 늘지 않아 커밋 잡음이 없다.

#### 손 편집을 막는다

각 스냅샷에 해시(SHA-256)를 넣고 검사가 다시 계산해 대조한다. 검사를 통과하려고 스냅샷을 고치면 해시 불일치로 실패한다. 계약 번들을 `Contracts/upstream.lock.json`이 해시로 고정하는 것과 같은 패턴이다.

#### 클라우드가 필요해지는 지점

| 상황 | 커밋으로 되나 |
| --- | --- |
| 앱 여러 개가 한 백엔드를 씀 | 된다 |
| 앱이 다른 저장소에 있음 | 안 된다 |
| 실제 호출 빈도를 알고 싶음 | 안 된다 — 서버 로그가 필요하다 |

뒤 두 가지가 실제로 생기면 그때 다시 본다.

## 5. 어느 빌드가 무엇을 잡는가

백엔드 빌드에 iOS·Android 빌드를 넣지 않는다. 각자 자기 빌드에서 자기가 알아야 할 것을 안다.

| 언제 | 도는 것 | 잡는 것 | 비용 |
| --- | --- | --- | --- |
| `spfn:build` · `spfn:dev` 재시작 | 계약 생성 + 스냅샷 비교 | 공개 약속 위반 | JSON 비교, 밀리초 |
| 백엔드 CI | 위와 동일 | 위와 동일 | 초 단위 |
| 앱 빌드 (iOS·Android) | 계약 → 타입 생성 → 컴파일 | 앱 코드가 새 계약과 안 맞음 | 분 단위 |
| 앱 CI | 앱 빌드 + 사용 목록 기록 | 위와 동일 | 앱 배포 전에만 |

**앱 빌드에 Node가 필요 없다.** 앱 빌드는 커밋된 계약 JSON만 읽는다. 계약 생성은 백엔드 빌드에서만 일어난다.

| 상황 | 앱 빌드 필요? |
| --- | --- |
| 백엔드 라우트 수정·삭제 | 아니오 — 계약 검사가 잡는다 |
| 앱 화면 코드 수정 | 예 — 원래 하던 일 |
| 앱 배포 | 예 — 원래 하던 일 |

| 3 | `.contract()` 표시 + 스냅샷 비교 검사 + `released/` 관리 | spfn | 2 |
| 4 | 타입 문법 4종 확장 (계약 스키마 + 양 플랫폼 코드젠) | spfn + spfn-mobile | — |
| 5 | 모바일 계약 생성기 | spfn | 2, 3, 4 |
| 6 | 앱 계약을 읽는 모바일 코드젠 경로 (SwiftPM 플러그인 / Gradle 태스크) | spfn-mobile | 4, 5 |
| 7 | 사용 목록 기록 + 데드 API 리포트 | spfn-mobile | 6 |
| 8 | 연산 단위 가용성 + 최소 지원 버전 + `appUpdateRequired` | spfn + spfn-mobile | 1, 5, 6 |

0은 이 설계와 무관하게 지금 존재하는 불일치이고 실서버 왕복이 이것부터 만난다. 1은 검사기가 이미 있으므로 헤더와 호출부만 붙이면 된다. 2와 4는 독립이라 병렬로 갈 수 있다.

## 7. 케이스 표를 닫아야 하는 지점

컨벤션대로 착수 전에 유한 표로 닫는다.

- **타입 매핑 표**: 계약 타입(스칼라 4 + array + named + map + enum) × 대상 언어(Swift·Kotlin) × 옵셔널 여부 → 생성 결과.
- **계약 변경 판정 표**: 변경 종류(연산 추가·제거·필드 추가·제거·타입 변경·옵셔널화·경로 변경) × 이전 스냅샷 유무 → 통과/실패.
- **계약 불일치 표**: 앱 계약 버전 × 서버 계약 버전(같음·앱이 낮음·앱이 높음·범위 밖) × 연산 존재 여부 → 기대 진단.

나머지는 표로 닫히지 않아 리뷰 대상이다.

## 8. 위험

| 위험 | 내용 |
| --- | --- |
| 스냅샷 사슬이 끊김 | 릴리스마다 스냅샷을 남기지 않으면 전이 논증이 깨진다. 릴리스 명령이 스냅샷 생성을 강제해야 한다 |
| 사용 목록의 조용한 실패 | R8·링크맵 리포트를 못 읽었는데 "쓰는 앱 없음"으로 읽으면 지우면 안 될 것을 지운다. 등록부 P7 — 읽기 실패와 결과 없음을 구분해야 한다 |
| 타입 문법 확장의 양 플랫폼 갈림 | 새 타입 4종이 Swift·Kotlin에서 다르게 표현되면 등록부 P9의 재발이다. 공유 벡터 표로 고정한다 |
| `.contract()` 미부착 | 공개해야 할 라우트에 표시를 잊으면 아무 보호도 없다. 다만 실패 방향이 안전하다 — 계약에 안 실리므로 앱이 부를 수 없다 |
| 범위 확대 | 유니온·제네릭 요구가 곧 나온다. D-D의 4종 경계를 지키고 넘으면 별도 결정으로 올린다 |

## 9. 이 설계가 답하지 않는 것

- 서버가 옛 계약을 언제까지 받아줄지 — 앱 강제 업데이트 정책과 얽힌다
- 파일 업로드(`formData`)를 모바일이 어떻게 다룰지 — 계약에 multipart 표현이 없다
- 실시간(WebSocket·SSE) — 계약은 REST 연산만 담는다
